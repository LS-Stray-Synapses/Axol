# ADR-0004: Per-conversation sessions: the server owns what the model saw

## Context

The web UI gained conversations and folders (see [Front end](../Architecture/Front%20end.md)). The prototype server kept **one** model history (`agent.messages`) for the whole process, so every chat shared one context: the model "remembered" other chats, and a restart forgot everything.

Chat products (ChatGPT, DeepSeek's apps) and the DeepSeek harness all solve this the same way: the server keeps a separate history per conversation, and the client names the conversation it is talking to. dsh goes further and makes an append-only session log the source of truth ([DeepSeek harness](../Research/DeepSeek%20harness.md), idea 5), which is also what [ADR-0003](ADR-0003-experience-store.md) asks for.

## Decision

- Every `user_message` carries a `conversation_id` (generated by the browser).
- The server keeps each conversation's model-visible messages (user, assistant, tool) in an **append-only log**, `sessions/<id>.jsonl` (`modules/sessions.py`). A turn loads the log, runs the agent on it, and appends what the turn added, even if the turn was cancelled or failed.
- The system prompt is **not** logged: it is rebuilt every turn, so long-term memory saved in any chat reaches every chat.
- The browser keeps the **presentation**: titles, folders, rendered thinking blocks, speed stats (`web/src/conversations.ts`, in localStorage). Deleting a chat also deletes its log (`sessions.delete` operation).
- A `user_message` without an id falls back to the old shared history, so older clients keep working.

## Consequences

- Positive: chats are isolated; context survives server restarts; the logs are a first concrete run log for the Experience Store.
- Negative: two stores share the id but can drift. Clearing the browser orphans server logs, and deleting a log makes the model forget a chat the UI still shows. Chats created before this change have no log, so the model starts them fresh.
- Negative: cancelled tool calls get a synthetic "cancelled by the user" result, so the history stays valid for OpenAI-compatible servers.
- Follow-up: move titles and folders server-side too (a `sessions.list` operation), so the server is the single source of truth and chats can sync across browsers. Log thinking and token metrics as well, as dsh does.
